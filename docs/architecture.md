# Platform Architecture & Engineering Decisions

## 1. System Overview and Architectural Boundaries

Milestone 1 implements the foundational vertical slice of the Healthcare Multi-Agent AI Platform. The system follows the **Clean Architecture / Hexagonal Architecture** principles, enforcing strict dependency boundaries between data contracts, business workflows, and external LLM providers.

### Dependency Graph

```
[CLI / Main Entrypoint] (Composition Root)
         │
         ▼
    [TextAgent]
         │
         ▼
 [ExtractionWorkflow] ──► [ClinicalFieldExtractor Interface]
         │                               │
         │                               ▼
         │                      [GroqFieldExtractor Adapter]
         ▼
[TextChunker] + [EvidenceValidator] + [ValueParser] + [DateParser] + [CandidateDeduplicator]
```

### Architectural Invariants Enforced by AST Tests
1. `contracts.py` must NEVER import `groq`, `healthcare_agents.workflow`, `healthcare_agents.text_agent`, or `healthcare_agents.groq_extractor`. It defines pure Pydantic v2 schemas and standard library types.
2. `workflow.py` must NEVER directly import the Groq SDK. It relies exclusively on the `ClinicalFieldExtractor` abstract interface.
3. `text_agent.py` must NEVER instantiate network clients directly. It orchestrates bundle creation and invokes the injected `ExtractionWorkflow`.

## 2. Source Text Preservation and Coordinate Policy

Evidence traceability is a core medical requirement. In legal and clinical environments, every extracted entity must point to the exact characters in the original record.

### Code-Point Offset Policy
- Offsets represent **zero-based Python Unicode code points** (`len(str)`), not UTF-8 byte offsets. This ensures consistent string indexing across Windows and Unix platforms.
- Source text is **never normalized, rewritten, or trimmed** when computing offsets.
- Segment slicing invariant:
  $$\text{source\_text}[\text{seg.start\_offset} : \text{seg.end\_offset}] \equiv \text{seg.exact\_text}$$

### Quotation Matching Hierarchy
1. **Exact Substring Matching**: The quotation provided by the extractor is located within the target segment using direct substring searching (`str.find`).
2. **Duplicate Disambiguation**: If a quotation occurs more than once within the referenced segment, the quotation is marked as `ambiguous_match`. The system strictly avoids guessing or arbitrarily picking the first occurrence.
3. **Tokenized Whitespace Fallback**: If an exact match fails due to minor formatting differences (e.g. model collapsed consecutive spaces or newlines into a single space), the system tokenizes the segment into non-whitespace words while retaining exact start and end character coordinates of each word in the untouched text. If a unique sequence of tokens matches, the original start and end offsets are derived directly from the bounding tokens.
4. **Unicode Normalization Fallback**: NFC normalization may be used to verify that combining accents/matras match, but coordinates are only emitted if the character span maps unambiguously back to the untouched text.

## 3. Strict Provider Schema vs Internal Domain Models

The platform enforces a strict separation between provider-facing transmission schemas and internal domain models.

### Why Provider Schemas Must Be Separate
1. **JSON Schema Strictness**: Groq and OpenAI structured outputs require `strict: true`, which mandates that `additionalProperties: false` is set on every object, and all properties must be declared in the `required` array.
2. **Nullable Representation**: Optional fields in LLM responses are represented using explicit union types (`["string", "null"]`) or empty strings.
3. **Internal Domain Richness**: Domain models (`FactCandidate`, `AgentResult`) contain rich parsed types, validation statuses, audit histories, conflict warning cross-references, and timing metadata that must never be generated by or sent to the LLM.

## 4. Chunking and Call Budget Enforcement

Clinical documents can exceed single-prompt token limits or context windows.

### TextChunker Mechanics
- **Max Input Limit**: Configurable `MAX_TEXT_CHARS=36_000` (rejects oversized inputs before provider invocation).
- **Chunk Size Limit**: `MAX_LLM_CHARS_PER_CHUNK=6_000`.
- **Semantic Boundary Preference**: Chunks group whole paragraphs and sentences. If a single continuous paragraph exceeds 6,000 characters, it is broken on sentence endings (`. `, `? `, `! `, `। `).
- **Hard Split Overlap**: If an unbroken token run forces a hard split, a 200-character overlap is used for context continuity, with fragments tracking `parent_segment_id` and exact parent offsets.
- **Budget Gating**: `MAX_LLM_CALLS_PER_REQUEST=8`. Actual attempts (including retries) are tracked. If the call budget is exhausted, processing halts gracefully, and a `partial` result is emitted with the IDs of all unprocessed chunks.

## 5. Deduplication and Conflict Detection

### Deduplication
Overlapping chunks or redundant mentions can produce duplicate facts. A candidate is deduplicated only if:
- Normalized label, raw value, unit, date/time, assertion status, temporality, and experiencer match identically.
- AND the evidence quotation represents the **same original source span**.
Separate occurrences of the same clinical fact at different coordinates are preserved as distinct observations.

### Defensible Conflict Detection
Conflicts are flagged only when observations share an explicit grouping context:
- Same normalized label (e.g. `fasting glucose`),
- Same explicit observation date/time,
- Same experiencer (`patient`),
- BUT differing raw values (`95 mg/dL` vs `145 mg/dL`) or incompatible units.
When a conflict is detected, both observations are preserved, cross-referenced via `conflict_warning_refs`, and highlighted in pipeline warnings.
